# สถาปัตยกรรมระบบ 

## ภาพรวม: ข้อมูล 1 ค่าเดินทางยังไง

ลองตามข้อมูลความสั่น 1 ค่า ตั้งแต่เกิดจนขึ้นหน้าจอ:

1. **อุปกรณ์วัดค่า:** ESP32 เก็บตัวอย่างการสั่น 20 ครั้ง/วินาที แล้วคำนวณ RMS ออกมาเป็นค่าเดียว (edge processing) ส่วนตัวจำลองใช้สมการใน `machine_model.py`
2. **ส่งเข้า MQTT:** อุปกรณ์ publish JSON ไปที่ `factory/line1/M03/telemetry` ด้วย QoS 1
3. **Broker กระจาย:** Mosquitto ส่งต่อให้ทุกคนที่ subscribe หัวข้อนั้นไว้ ในที่นี้คือ backend ที่ subscribe `factory/+/+/telemetry`
4. **Backend ตรวจสอบ** (`ingest.py`): JSON ถูกต้องไหม, มีครบทุกฟิลด์ไหม, เวลาสมเหตุสมผลไหม, seq ข้ามไปหรือเปล่า (ข้อมูลหาย)
5. **วิเคราะห์** (`analytics.py`): อัปเดตประวัติของเครื่อง แล้วรันกฎตรวจจับทั้งหมด ได้ผลเป็น health score, RUL และ alert
6. **บันทึก** (`db.py`): เขียน telemetry และอัปเดตสถานะเครื่องใน transaction เดียว
7. **Push:** ส่งผ่าน WebSocket ไปทุกหน้า dashboard ที่เปิดอยู่ กราฟจึงขยับทันที

คำสั่งไหลกลับทิศ: ผู้ใช้กดปุ่ม → `POST /api/machines/M03/command` → backend publish ไป `.../cmd` → อุปกรณ์ทำตาม → อุปกรณ์ publish `.../ack` → dashboard ขึ้นข้อความ "ยืนยันคำสั่งแล้ว"

## ทำไมเลือกเทคโนโลยีแต่ละตัว

| เลือก | แทนที่จะใช้ | เหตุผล |
|---|---|---|
| **MQTT** | HTTP POST จากอุปกรณ์ | Header เล็กมาก ประหยัดเน็ตและแบตเตอรี่, เชื่อมต่อค้างไว้ได้ทำให้ส่งคำสั่งกลับลงอุปกรณ์ได้ทันที, มี QoS / Last Will / retained message ในตัว |
| **Mosquitto** | broker บน cloud | ฟรี เบา รันใน Docker ได้ เป็นมาตรฐานที่ใช้กันทั่วไป |
| **FastAPI + asyncio** | Flask | งานเป็น I/O ล้วน (รอ MQTT รอ DB รอ WebSocket) ใช้ async ก็รับได้หลายพันข้อความต่อวินาทีใน process เดียว และได้ Swagger docs ฟรี |
| **PostgreSQL** | MongoDB | ข้อมูลมีโครงสร้างชัด ต้อง JOIN ระหว่างเครื่อง/telemetry/alert และย้ายไป TimescaleDB (extension ของ Postgres) ได้ง่ายเมื่อข้อมูลโต |
| **WebSocket** | ให้หน้าเว็บ polling ทุกวินาที | Server push ทันทีเมื่อมีข้อมูลใหม่ ไม่เปลือง request เปล่าๆ |
| **กฎทางสถิติ** | Deep learning | ยังไม่มีข้อมูลจริงที่ติดป้ายว่าเครื่องเสียเมื่อไร, กฎอธิบายได้ (ช่างเชื่อถือ), และไม่ต้อง train เลยเริ่มใช้ได้ทันที |

## การออกแบบ MQTT Topic

```
factory / <line> / <machine_id> / <telemetry|status|cmd|ack>
```

- **เรียงจากใหญ่ไปเล็ก** (โรงงาน → ไลน์ → เครื่อง → ประเภทข้อความ) จะได้ subscribe ด้วย wildcard ตามต้องการ เช่น `factory/line1/#` คือทุกอย่างของไลน์ 1 หรือ `factory/+/+/status` คือสถานะของทุกเครื่อง
- **แยก telemetry กับ status ออกจากกัน** เพราะ status ต้องเป็น retained (คนที่เพิ่ง subscribe จะรู้สถานะล่าสุดทันที) แต่ telemetry ไม่ควร retained
- **ทุกข้อความใช้ QoS 1** (ส่งถึงอย่างน้อย 1 ครั้ง): ข้อมูลเซนเซอร์ที่หายไปอาจเป็นช่วงที่เครื่องเริ่มเสียพอดี ส่วนข้อความซ้ำไม่ทำให้การวิเคราะห์ผิด QoS 2 ไม่จำเป็นและช้ากว่า

## การรับมือเมื่อของเสีย (Reliability)

| ปัญหา | ระบบรู้ได้ยังไง | รับมือยังไง |
|---|---|---|
| อุปกรณ์ดับ / เน็ตหลุด | broker ส่ง **Last Will** "offline" แทนอุปกรณ์ เมื่อเงียบเกิน keepalive | ขึ้นจุดแดงบน dashboard + alert |
| เฟิร์มแวร์ค้าง แต่ TCP ยังต่ออยู่ | **Watchdog** ใน backend: สถานะ online แต่ไม่มีข้อมูลเกิน 3 รอบ | สถานะ `stale` + alert; บนบอร์ดเอง hardware WDT จะรีเซ็ตบอร์ด |
| ข้อความหายระหว่างทาง | **seq** ข้ามเลข | นับเป็น % ข้อมูลหาย (มุมขวาบนของ dashboard) |
| เน็ตหลุดช่วงสั้นๆ | อุปกรณ์ publish ไม่สำเร็จ | **Store-and-forward:** เก็บใส่บัฟเฟอร์ (จำกัดขนาด) แล้วส่งย้อนหลังพร้อม `buffered=true` และเวลาเดิมที่วัดได้ |
| Broker / DB ล่ม | exception | backend ต่อใหม่เองทุก 3 วินาที, อุปกรณ์ใช้ exponential backoff |
| JSON เสีย / ค่าแปลก | validate ตอนรับ | ทิ้งข้อความนั้นแล้วเขียน log ระบบไม่ล่ม |

## ส่วนวิเคราะห์ข้อมูล: แต่ละกฎจับอะไร

| กฎ | จับอะไร | ทำไมต้องมี |
|---|---|---|
| **Threshold** (median 5 ค่า) | ค่าเกินเกณฑ์มาตรฐาน | เข้าใจง่ายที่สุด แต่ใช้ median แทนค่าล่าสุด spike ครั้งเดียวจึงไม่ทำให้เกิด critical หลอก |
| **Robust z-score** | ค่ากระโดดผิดจากพฤติกรรมปกติของเครื่องนั้น | แต่ละเครื่องมีค่าปกติไม่เท่ากัน ใช้ MAD แทน std เพื่อให้ทนต่อ outlier |
| **Level shift** | ค่ายกระดับขึ้นแล้วค้างไว้ | แยก "เกิดครั้งเดียว" ออกจาก "เปลี่ยนสภาวะ" และล้างประวัติเพื่อไม่ให้ RUL ลากเส้นผ่านขั้นบันได |
| **Stuck sensor** | ค่าเดิมเป๊ะติดกันหลายครั้ง | เซนเซอร์เสียก็ต้องแจ้ง แต่ต้องแยกจาก "เครื่องเสีย" |
| **RUL** | แนวโน้มเสื่อมช้าๆ | กฎอื่นจะเห็นก็ต่อเมื่อค่าใกล้เกณฑ์แล้ว แต่เส้นแนวโน้มบอกล่วงหน้าได้ว่าจะถึงจุดพังเมื่อไร |

## ข้อจำกัดที่รู้อยู่ (ควรพูดเองก่อนกรรมการถาม)

- ข้อมูลทั้งหมดเป็นข้อมูลจำลอง ผลประเมินจึงพิสูจน์ได้แค่ว่าตรรกะทำงานตามที่ออกแบบ ยังไม่ได้พิสูจน์ความแม่นยำกับเครื่องจริง
- สถานะของ analyzer อยู่ในหน่วยความจำ ถ้า restart backend ต้องเก็บประวัติใหม่ (แก้ได้โดยโหลดจาก DB ตอนเริ่ม)
- ยังไม่มี authentication ทั้ง MQTT และ API
- backend มี process เดียว ถ้าจะ scale ต้องใช้ shared subscription ของ MQTT v5 หรือคั่นด้วย message queue
