# สถาปัตยกรรมระบบ

## ภาพรวม: เส้นทางของข้อมูลหนึ่งค่า

ส่วนนี้อธิบายเส้นทางของค่าความสั่นสะเทือนหนึ่งค่า ตั้งแต่ถูกวัดจนแสดงผลบนหน้าจอ

1. **การวัดค่าที่อุปกรณ์:** ESP32 เก็บตัวอย่างความสั่นสะเทือน 20 ครั้งต่อวินาที แล้วคำนวณเป็นค่า RMS เพียงค่าเดียวที่ตัวอุปกรณ์ หรือที่เรียกว่า edge processing ส่วนตัวจำลองใช้สมการใน `machine_model.py`
2. **การส่งเข้า MQTT:** อุปกรณ์ publish ข้อมูล JSON ไปยัง `factory/line1/M03/telemetry` ด้วย QoS 1
3. **การกระจายข้อความของ broker:** Mosquitto ส่งต่อข้อความให้ทุก client ที่ subscribe หัวข้อนั้น ซึ่งในที่นี้คือ backend ที่ subscribe `factory/+/+/telemetry`
4. **การตรวจสอบที่ backend** ใน `ingest.py`: ตรวจว่า JSON ถูกต้อง มีฟิลด์ครบถ้วน เวลาสมเหตุสมผล และเลข seq ไม่ขาดหาย ซึ่งบ่งชี้ว่าข้อมูลสูญหาย
5. **การวิเคราะห์** ใน `analytics.py`: ปรับปรุงประวัติของเครื่อง แล้วประมวลผลกฎตรวจจับทั้งหมด ได้ผลลัพธ์เป็น health score, RUL และ alert
6. **การบันทึก** ใน `db.py`: บันทึก telemetry และปรับปรุงสถานะเครื่องภายใน transaction เดียวกัน
7. **การส่งข้อมูลไปยังหน้าจอ:** ส่งผ่าน WebSocket ไปยัง dashboard ทุกหน้าที่เปิดอยู่ กราฟจึงอัปเดตทันที

คำสั่งควบคุมเดินทางในทิศทางตรงกันข้าม: ผู้ใช้กดปุ่ม → `POST /api/machines/M03/command` → backend publish ไปยัง `.../cmd` → อุปกรณ์ดำเนินการตามคำสั่ง → อุปกรณ์ publish `.../ack` → dashboard แสดงข้อความ "ยืนยันคำสั่งแล้ว"

## เหตุผลในการเลือกเทคโนโลยี

| เทคโนโลยีที่เลือก | ทางเลือกอื่น | เหตุผล |
|---|---|---|
| **MQTT** | HTTP POST จากอุปกรณ์ | header มีขนาดเล็ก ช่วยประหยัดแบนด์วิดท์และพลังงาน การเชื่อมต่อที่คงค้างไว้ทำให้ส่งคำสั่งกลับไปยังอุปกรณ์ได้ทันที และมี QoS, Last Will และ retained message ในตัว |
| **Mosquitto** | broker บนคลาวด์ | ไม่มีค่าใช้จ่าย ใช้ทรัพยากรน้อย รันใน Docker ได้ และเป็นมาตรฐานที่ใช้กันแพร่หลาย |
| **FastAPI + asyncio** | Flask | งานส่วนใหญ่เป็นการรอ I/O ทั้งจาก MQTT ฐานข้อมูล และ WebSocket การใช้ async ทำให้รองรับได้หลายพันข้อความต่อวินาทีใน process เดียว และได้เอกสาร Swagger โดยอัตโนมัติ |
| **PostgreSQL** | MongoDB | ข้อมูลมีโครงสร้างชัดเจน ต้อง JOIN ระหว่างตารางเครื่องจักร telemetry และ alert และสามารถย้ายไปใช้ TimescaleDB ซึ่งเป็น extension ของ PostgreSQL ได้ง่ายเมื่อข้อมูลมีปริมาณมากขึ้น |
| **WebSocket** | ให้หน้าเว็บ polling ทุกวินาที | server ส่งข้อมูลได้ทันทีเมื่อมีข้อมูลใหม่ โดยไม่สิ้นเปลือง request ที่ไม่มีข้อมูล |
| **กฎทางสถิติ** | Deep learning | ยังไม่มีข้อมูลจริงที่ระบุว่าเครื่องเสียเมื่อใด กฎทางสถิติอธิบายเหตุผลได้ ทำให้ช่างเทคนิคเชื่อถือ และใช้งานได้ทันทีโดยไม่ต้องฝึกโมเดล |

## การออกแบบ MQTT Topic

```
factory / <line> / <machine_id> / <telemetry|status|cmd|ack>
```

- **เรียงลำดับจากระดับใหญ่ไปเล็ก** ได้แก่ โรงงาน ไลน์การผลิต เครื่องจักร และประเภทข้อความ เพื่อให้ subscribe ด้วย wildcard ได้ตามต้องการ เช่น `factory/line1/#` สำหรับข้อมูลทั้งหมดของไลน์ 1 หรือ `factory/+/+/status` สำหรับสถานะของทุกเครื่อง
- **แยก telemetry ออกจาก status** เนื่องจาก status ต้องเป็น retained message เพื่อให้ client ที่เพิ่ง subscribe ทราบสถานะล่าสุดทันที ขณะที่ telemetry ไม่ควรเป็น retained message
- **ทุกข้อความใช้ QoS 1** ซึ่งรับประกันการส่งถึงอย่างน้อยหนึ่งครั้ง เนื่องจากข้อมูลเซนเซอร์ที่สูญหายอาจตรงกับช่วงที่เครื่องเริ่มเสียพอดี ส่วนข้อความซ้ำไม่ส่งผลต่อความถูกต้องของการวิเคราะห์ จึงไม่จำเป็นต้องใช้ QoS 2 ซึ่งช้ากว่า

## การรับมือกับความขัดข้อง

| ปัญหา | วิธีตรวจพบ | วิธีรับมือ |
|---|---|---|
| อุปกรณ์ดับหรือเครือข่ายขัดข้อง | broker ส่ง **Last Will** "offline" แทนอุปกรณ์เมื่อขาดการติดต่อเกินเวลา keepalive | แสดงสถานะสีแดงบน dashboard และสร้าง alert |
| เฟิร์มแวร์ค้างแต่การเชื่อมต่อ TCP ยังคงอยู่ | **Watchdog** ใน backend ตรวจพบว่าสถานะเป็น online แต่ไม่มีข้อมูลเกิน 3 รอบ | กำหนดสถานะเป็น `stale` และสร้าง alert ส่วนบนบอร์ด hardware watchdog จะรีเซ็ตบอร์ดเอง |
| ข้อความสูญหายระหว่างทาง | เลข **seq** ขาดหาย | คำนวณเป็นร้อยละของข้อมูลที่สูญหาย และแสดงที่มุมขวาบนของ dashboard |
| เครือข่ายขัดข้องชั่วคราว | อุปกรณ์ publish ไม่สำเร็จ | **Store-and-forward:** เก็บข้อมูลในบัฟเฟอร์ที่จำกัดขนาด แล้วส่งย้อนหลังพร้อม `buffered=true` และเวลาที่วัดได้จริง |
| Broker หรือฐานข้อมูลล่ม | เกิด exception | backend เชื่อมต่อใหม่ทุก 3 วินาที และอุปกรณ์ใช้ exponential backoff |
| JSON ผิดรูปแบบหรือค่าผิดปกติ | ตรวจสอบความถูกต้องเมื่อรับข้อมูล | ละทิ้งข้อความนั้นและบันทึก log โดยระบบยังทำงานต่อได้ |

## การวิเคราะห์ข้อมูล: หน้าที่ของแต่ละกฎ

| กฎ | สิ่งที่ตรวจจับ | เหตุผลที่ต้องมี |
|---|---|---|
| **Threshold** ใช้ค่ามัธยฐานของ 5 ค่าล่าสุด | ค่าที่เกินเกณฑ์มาตรฐาน | เป็นกฎที่เข้าใจง่ายที่สุด และการใช้ค่ามัธยฐานแทนค่าล่าสุดช่วยป้องกัน critical alert ที่เกิดจาก spike เพียงครั้งเดียว |
| **Robust z-score** | ค่าที่เบี่ยงเบนจากพฤติกรรมปกติของเครื่องนั้น | แต่ละเครื่องมีค่าปกติแตกต่างกัน และการใช้ MAD แทนส่วนเบี่ยงเบนมาตรฐานช่วยให้ทนต่อ outlier |
| **Level shift** | ค่าที่เปลี่ยนระดับแล้วคงอยู่ที่ระดับใหม่ | แยกเหตุการณ์ที่เกิดครั้งเดียวออกจากการเปลี่ยนสภาวะ และล้างประวัติเพื่อไม่ให้การประเมิน RUL ลากเส้นแนวโน้มผ่านจุดที่ค่าเปลี่ยนระดับ |
| **Stuck sensor** | ค่าเดิมซ้ำกันติดต่อหลายครั้ง | ความผิดปกติของเซนเซอร์ต้องแจ้งเตือนเช่นกัน แต่ต้องแยกออกจากความผิดปกติของเครื่อง |
| **RUL** | แนวโน้มการเสื่อมสภาพอย่างช้าๆ | กฎอื่นตรวจพบได้ก็ต่อเมื่อค่าใกล้ถึงเกณฑ์แล้ว แต่เส้นแนวโน้มสามารถคาดการณ์ล่วงหน้าได้ว่าเครื่องจะถึงจุดขัดข้องเมื่อใด |

## ข้อจำกัดที่ทราบ

- ข้อมูลทั้งหมดเป็นข้อมูลจำลอง ผลการประเมินจึงยืนยันได้เพียงว่าตรรกะทำงานตามที่ออกแบบไว้ แต่ยังไม่ได้ยืนยันความแม่นยำกับเครื่องจักรจริง
- สถานะของส่วนวิเคราะห์เก็บอยู่ในหน่วยความจำ เมื่อ restart backend จะต้องสะสมประวัติใหม่ ซึ่งแก้ไขได้โดยโหลดข้อมูลจากฐานข้อมูลเมื่อเริ่มทำงาน
- ยังไม่มีระบบยืนยันตัวตนทั้งฝั่ง MQTT และ API
- backend ทำงานใน process เดียว หากต้องการขยายระบบต้องใช้ shared subscription ของ MQTT v5 หรือใช้ message queue คั่นกลาง
